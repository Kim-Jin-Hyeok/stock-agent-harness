# KIS 종목 마스터 유형 매핑 근거 재검증

## 판정과 범위

2026-10-05 KIS 공식 저장소의 규격·예제 4개를 commit과 바이트 해시로 고정하고, 기존 보존 배치의 4,403행과 대조했다. **필드 위치와 조합별 건수는 일치하지만, ETP 공백과 미정의 코드의 의미는 이번 자료로도 확인하지 못했다.** 공백을 `0`으로 바꾸는 규칙과 전체 개별주 자동 분류는 보류한다.

고정한 규격의 필드 설명과 실제 조합이 일치하는 범위는 KOSPI `EF/2/0` 1,159행의 ETF 유형 해석이다. 이는 아래에서 정한 프로젝트의 제한적인 해석 방향이며, 원천이 모든 조합의 허용 여부를 인증했다는 뜻은 아니다. 나머지 3,244행은 공백 또는 미정의 값 때문에 전체 조합 매핑을 보류한다. **이 건수는 문서의 조합 검토 결과이지 운영 분류 결과나 종목 자격 판정 건수가 아니다.**

이 문서의 근거 재검증 단계에서는 Java 매핑·새 enum·`StockEligibilityInput`·DB 저장·운영 후보·백테스트·주문 연결을 추가하지 않았다. 후속 Java 정책의 구현과 검증은 마지막 절의 별도 문서로 구분한다. `DESIGN_ONLY`, `runtimeSelectionImplemented=false`, `eligibilityOrHistoricalPopulationVerified=false`를 유지한다. 유형 해석과 과거 시장 소속·상장 상태·정보 가용성 검증은 별개의 책임이다.

GitHub API의 commit 시각은 `2026-09-28T07:59:21Z`, 이번 파일 보존 시각은 `2026-10-05T11:22:18.6980272+00:00`다. 어느 시각도 마스터의 적용일·당시 공개 시각으로 사용하지 않는다. 이번에 고정한 버전을 과거 원천 조사에서 사용한 버전이라고 소급하지 않는다.

## 필드 정의와 바이트 위치

두 헤더는 증권 그룹의 `ST`·`EF`·`FE` 등을 설명하며 `EN`·`PF`는 설명하지 않는다. ETP 필드는 KOSPI에서 `0`~`5`, KOSDAQ에서 `0`~`4`를 설명한다. 두 시장 모두 ETP 공백·`8`·`9`의 의미와 공백을 `0`으로 간주한다는 규칙은 명시하지 않는다. 우선주 필드는 `0`·`1`·`2`를 설명하지만 `9`는 설명하지 않는다. 이는 [고정한 KOSPI 헤더](https://github.com/koreainvestment/open-trading-api/blob/277ec0eb7a9b7f63b6807829286c80f36649dad2/stocks_info/%EC%A2%85%EB%AA%A9%EB%A7%88%EC%8A%A4%ED%84%B0%EC%A0%95%EB%B3%B4%28%EC%BD%94%EC%8A%A4%ED%94%BC%29.h#L9-L33)와 [KOSDAQ 헤더](https://github.com/koreainvestment/open-trading-api/blob/277ec0eb7a9b7f63b6807829286c80f36649dad2/stocks_info/%EC%A2%85%EB%AA%A9%EB%A7%88%EC%8A%A4%ED%84%B0%EC%A0%95%EB%B3%B4%28%EC%BD%94%EC%8A%A4%EB%8B%A5%29.h#L9-L25)의 확인 범위다.

기존 관측의 앞부분 폭 `9 + 12 + 40` bytes를 기준으로, 헤더의 숫자 폭을 가진 필드와 예제의 `field_specs`를 순서대로 대조했다. KOSPI 70개·227 bytes, KOSDAQ 64개·221 bytes가 일치했다. 아래는 LF를 제외한 행 시작부터의 0-based 바이트 위치이며 기존 Java 원문 파서 계약과도 같다.

| 증권 그룹 | 2 | 61 | 61 |

예제는 필드 분리·정제 방법을 보여줄 뿐 세 필드의 허용 조합표나 미정의 코드 설명을 제공하지 않는다. 또한 공백 처리 후의 DataFrame 값을 마스터 원문 공백의 의미에 대한 증거로 사용하지 않는다. 이번에는 예제를 실행하지 않고 파일만 읽었으며 예제의 다운로드·TLS 검증 해제·ZIP 일괄 추출을 사용하지 않았다. [KOSPI 예제](https://github.com/koreainvestment/open-trading-api/blob/277ec0eb7a9b7f63b6807829286c80f36649dad2/stocks_info/kis_kospi_code_mst.py#L27-L78), [KOSDAQ 예제](https://github.com/koreainvestment/open-trading-api/blob/277ec0eb7a9b7f63b6807829286c80f36649dad2/stocks_info/kis_kosdaq_code_mst.py#L27-L78).

## 보존 원본의 전체 조합

대상은 [최초 실측](stock-master-collection-observation-01.md)의 배치 `4ebd57c2-dd69-4b99-86c7-8efed3e531f7`다. 원본을 다시 받지 않고 고정 규격에서 계산한 위치로 전체 행을 읽었다. 아래 건수는 이전 관측 JSON의 모든 조합별 건수와 일치했다. 표의 `SPACE`는 원본 한 칸 ASCII 공백이며 문자열 `SPACE`나 `0`으로 변환하지 않는다.

유형 해석 방향은 **프로젝트의 보수적인 설계 선택**이다. 세 필드 중 의미 미확인 값이 있으면 전체 조합을 보류한다. 알려진 한 필드로 미확인 필드의 의미를 메우거나 자동 우선순위를 부여하지 않는다. 표의 0은 이번 해당 시장에서 조합이 관측되지 않았다는 뜻이다.

## 기존 초안의 유지와 보류

다음 판정은 [기존 유형 매핑 초안](../../../../strategy/swing/validation/stock-eligibility-source-validation-01.md)의 후속 검토 결과다. 현재 코드를 변경하거나 새로운 런타임 상태 값을 정의하지 않는다.

| 기존 방향 | 이번 판정 |
| --- | --- |
| `ST + ETP 0 + 우선주 0`을 `COMMON_STOCK` 후보로 해석 | 각 필드의 설명은 유지한다. 그러나 해당 조합은 이번 원본에 0행이며 `ST + SPACE`를 같은 조합으로 치환하지 않는다. 관측 개별주 자동 매핑은 보류한다. |
| `ST + ETP 0 + 우선주 1/2`를 `PREFERRED_STOCK` 후보로 해석 | 필드 설명은 유지하되 실제 ETP 공백 조합의 자동 매핑은 보류한다. 우선주 `9`는 `1`·`2`로 합치지 않는다. |
| `EF` 또는 `FE`이면 `ETF` 후보 | 그룹만으로 모든 조합을 분류하지 않도록 범위를 좁힌다. 이번 원본에서는 `EF/2/0`만 제한적으로 해석하고 `EF/8/0`는 보류한다. `FE`는 관측되지 않았다. |
| ETP `3/4`이면 `ETN` 후보 | 필드 의미는 유지하되 실제 `EN/3/0`·`EN/4/0`의 전체 매핑은 그룹 정의 확인 전까지 보류한다. |
| KOSPI ETP `5`를 `OTHER` 방향으로 분류 | 필드 설명과 개별주로 추정하지 않는 방향은 유지한다. 실제 그룹 `PF`의 의미와 조합 확인 전에는 자동 `OTHER` 변환을 보류한다. KOSDAQ에 같은 규칙을 확장하지 않는다. |
| 숫자 6자리 필터 또는 이름으로 유형 보완 | 채택하지 않는다. 실제 `ST`의 `0001A0`도 원문 그대로 보존하고 유형과 주문 코드 검증을 분리한다. |
| 미확인 값을 null과 원문으로 보존 | 유지한다. 미확인을 보통주·확정 제외 유형 `OTHER`·자격 실패로 바꾸지 않는다. |

원천에 세 필드의 완전한 허용·상충 조합표가 없으므로, 정의가 없는 조합을 곧바로 상충 오류로 표시하지 않는다. 후속 분류에서는 알려진 설명끼리 서로 다른 유형을 가리키는 경우에도 임의 우선순위로 해결하지 않고 보류하는 방향이다. 예를 들어 ETF를 가리키는 그룹과 ETN을 가리키는 상품 값의 조합은 별도 확인 대상이다. 이는 프로젝트의 실패 조건 예시이며 이번 원본에서 관측한 조합은 아니다.

## 미확인 항목과 추가 확인 질문

제공자에게 다음 내용을 확인할 필요가 있다. 이번 작업에서 문의를 발송하거나 답변을 받은 것은 아니다.

1. ETP 필드의 ASCII 공백은 어떤 시장·그룹에서 어떤 의미이며 `0`과 동등한가? 명시적인 적용 범위가 있는가?
2. 그룹 `EN`·`PF`, ETP `8`·`9`, 우선주 `9`의 현행 정의와 변경 적용일은 무엇인가?
3. 그룹·ETP·우선주 간 허용 조합, 상충 시 우선순위와 미적용 필드의 표현은 무엇인가?
4. 고정한 공개 규격과 실제 배포 마스터가 같은 버전인지 어떻게 확인하는가? 규격 변경 이력이 제공되는가?
5. 현재 파일 소속·유형의 적용 시점과 공개 시각, 과거 파일·정정 이력을 별도로 확보할 수 있는가?

공백 정의를 끝내 확인하지 못하면 해당 조합은 미확인 상태로 남긴다. 향후 다른 공식 원천으로 보완하려면 식별자 연결과 적용·가용 시각을 검증하고 근거를 별도로 기록해야 한다. 동일 이름·현재 시세 조회·다수 행의 반복 관측만으로 의미를 확정하지 않는다. 과거 전체 모집단이나 실제 주문 가능성도 승인하지 않는다.

## 로컬 검증과 변경 경계

보존 규격·예제와 헬퍼는 Git 제외 경로 `build/stock-master-type-mapping-validation-01/`에 있다. `source-capture.json`은 네 파일의 크기·SHA-256·Git blob SHA-1·고정 URL을 기록한다. 해당 JSON의 SHA-256은 `2261f134ab3c8b1604005d913cb37c86e2b8339bdbbe4867d386d18c2c444314`다. 규격 보존 헬퍼의 공개 API 조회는 commit 1회·파일 4회이며 별도의 main 확인과 웹 열람·검색은 이 횟수에 포함하지 않는다. 마스터 ZIP 다운로드는 0회다.

## 후속 Java 유형 해석

별도 작업인 [현재 유형 해석 정책](../stock-master-type-classification.md)은 이 검토의 제한적 해석 방향을 Java로 고정했다. KOSPI `EF/2/0`만 ETF로 반환하고 그 밖의 조합은 null 유형과 보류 사유를 남긴다. 실제 보존 배치의 1,159행 해석·3,244행 보류를 확인했으며 원본과 고정한 규격은 변경하지 않았다. 원문 파서·배치 서비스의 계약 및 종목 자격·과거 모집단·운영 선택 미승인 경계는 그대로다.

후속 [KIS 종목 자격 대체 원천 검증](kis-stock-eligibility-source-validation-01.md)은 별도 주식기본조회 API의 공식 시장·그룹·보통주·우선주 코드 정의를 확인했다. 이 API 정의로 MST의 ETP 공백을 `0`으로 바꾸거나 기존 매핑 보류를 소급 해제하지 않는다. API는 모의투자 미지원이며 실제 응답·식별 연결·적용 시점 검증은 별도 준비가 필요하다.
