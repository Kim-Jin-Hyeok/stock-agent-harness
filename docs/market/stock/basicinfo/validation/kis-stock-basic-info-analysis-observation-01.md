기준 커밋은 `bc47465bac1ad6fcbcfaeaf7c95b4b501e2397d1`이다. 기존 분석 서비스·Runner·설정·Store·Parser와 정책을 사용했으며 운영 코드와 테스트, Gradle 설정, `.env`, Compose와 V1~V7 SQL은 변경하지 않았다. KIS·토큰·주문·OpenAI 호출이나 마스터 재다운로드는 실행하지 않았다.

마스터의 관측 구간은 `2026-10-05T09:32:35.795200200Z`부터 `09:32:36.202168500Z`다. API 관측과 약 이틀 다른 입력을 함께 분석한 것이며, 동시 관측·현재 신선도나 과거 정보 가용 시점을 검증한 결과가 아니다.

마스터의 ETP 공백은 그대로 유지되어 유형 정책이 `ETP_VALUE_UNVERIFIED`를 반환했다. 식별 대조에 성공한 API 유형 해석은 `TYPE_INTERPRETED`였고, 기존 통합 정책이 보통주 참고 유형을 보완했다. 마스터 공백을 임의로 `0`으로 바꿔 판정을 맞추지 않았다.

제한 일곱 항목 중 마스터의 거래정지·정리매매·SPAC·관리종목과 API의 거래정지·관리종목은 `N_OBSERVED`였다. 코스피 마스터의 투자주의환기 필드는 `FIELD_NOT_PROVIDED`로 남았다. 이 미제공을 N으로 치환하지 않아 최종 제한 사전 점검은 `REVIEW_REQUIRED`다. **이는 분석 실패도 투자 적격 승인도 아니다.**

## 실행 격리와 결과 재현

기존 `analyzeStockBasicInfo` Gradle task와 실제 `main`을 한 번 실행했다. 그 뒤 별도로 계획한 점검 프로세스에서 같은 전용 구성과 실제 Runner를 실행하고, Store 복원·분석 서비스와 정책 직접 호출의 전체 결과를 비교했다. 두 Runner의 요약은 관측 ID·수집 UUID·종목·해시·유형·상태·사유까지 동일했다. 후속 보존 비교 단계에서는 분석 프로세스를 다시 실행하지 않았다.

점검 프로세스에서는 다음을 확인했다.

- 등록 Entity는 `KisStockBasicInfoObservationEntity` 하나이고 ApplicationRunner도 분석 Runner 하나다.
- Broker·Harness·Agent·주문·KIS Provider·Client·OpenAI·스케줄러·웹 서버·Flyway·SQL 초기화와 HTTP Client 빈을 등록하지 않았다. 금지된 빈은 초기화 전에도 검사했다.
- 명시한 DB에 접속했고 점검 연결의 JDBC read-only와 `@@session.transaction_read_only=1`을 확인했다.
- 정상 분석 후 Hikari 풀의 `isClosed()`가 true였다. 실제 `main`도 완료 메시지와 풀 종료 로그를 남기고 종료 코드 0으로 끝났다.

DB 인증정보는 기존 컨테이너에서 메모리로만 읽어 필요한 자식 프로세스 환경으로 전달했다. 명령행이나 증적에 비밀번호를 넣지 않았고, 자식 환경은 필요한 OS·Java·Gradle·DB 설정만 허용했다. `.env`의 내용은 로드하지 않고 보존 확인용 해시만 비교했으며 KIS·OpenAI 키를 전달하지 않았다. 읽기 전용 세션은 이번 검증 설정이며 DB 사용자 자체를 읽기 전용 권한으로 변경한 것은 아니다.

외부 호출 없음은 이 실행기의 구성·코드 경로와 점검 빈 목록에 대한 확인이다. 물리 네트워크 패킷이나 다른 프로세스의 계정 전체 호출을 측정한 것은 아니다. 로컬 MySQL 접속은 수행했다.

## DB와 파일 보존

검증 전 다른 DB 접속자와 활성화된 DB 이벤트가 각각 0개임을 확인했다. `event_scheduler`는 ON이었으나 활성 이벤트가 없어 설정을 변경하지 않았다. 복제 구성은 없었고 투자 앱은 검증 내내 중지 상태였다.

파일 비교에는 마스터 7개 원본, 기존 API 수신 바이트, 전체 `src` 소스·테스트·리소스, `.env`, Compose와 `build.gradle`이 포함된다. 검증 문서와 새 로컬 보조 도구는 보존 비교 대상이 아니라 이번 작업의 산출물이다.

## 중단 이력과 종료

초기 사전 점검 두 번은 DB 기동 전에 중단했다. 첫 번째는 기존 도구가 `docker.exe`와 `docker` 두 실행 경로를 함께 반환받아 프로세스를 시작하지 못한 문제였다. 로컬 보조 도구에서 `docker.exe` 하나를 선택하도록 수정했다. 두 번째는 샌드박스 내 Docker 자식 프로세스 접근 실패였고 승인된 실행에서 컨테이너 상태 조회가 성공했다. 기존 운영 도구는 변경하지 않았다.

실제 분석 두 프로세스는 모두 정상 완료했다. 이후 로그에서 DB 사용자명 `stock`을 마스킹하면서 완료 문구의 같은 문자열도 가려져 요약 비교가 중단됐다. MySQL은 이때도 정상 종료했다. 실패 증적을 유지하고 저장된 로그를 마스킹된 형식으로 비교했다. 보존 비교 도구의 PowerShell JSON 배열 처리도 바로잡은 뒤 남은 DB·파일 비교만 진행했다. 이 과정에서 분석·토큰·API를 자동 재실행하거나 기존 증적을 덮어쓰지 않았다.

최종 보존 비교는 `2026-10-07T04:40:40.3523747Z`에 `PASSED`로 완료됐다. MySQL의 `04:40:36.998397Z` `Shutdown complete` 로그, 종료 코드 `0`, `OOMKilled=false`를 확인했다. 처음부터 존재하던 컨테이너와 볼륨을 유지했고 최종 MySQL·투자 앱은 모두 `exited`다. 투자 앱의 시작 시각과 컨테이너 ID도 변하지 않았다.

| 실행 구간 | 소요시간 |
| --- | --- |
| 실제 Gradle 분석 자식 프로세스 | 약 `15.57초`, 종료 코드 0 |
| 별도 점검 Java 자식 프로세스 | 약 `5.59초`, 종료 코드 0 |
| 점검 내부의 Context·분석·대조·풀 종료 | 약 `4.37초` |

이 시간은 한 번의 로컬 실행 관측값이다. Gradle·JVM 기동을 포함한 프로세스 시간과 분석 내부 시간이 다르며 외부 API 응답 시간이나 운영 처리량을 의미하지 않는다.

## 증적과 변경 범위

증적 루트는 Git 제외 경로 `build/kis-stock-basic-info-analysis-observation-01/`다. SQL 덤프에는 개인 투자 데이터가 포함될 수 있어 Git에 추가하거나 공개 출력하지 않는다.

| 경로 | 내용 |
| --- | --- |
| `verification-summary.json`, `evidence-manifest.json` | 최종 통합 판정과 증적별 길이·해시 |
| `run-01/`, `run-02/` | DB 기동 전 사전 점검 실패 기록 |
| `run-03/` | 실제 Gradle·점검 실행 로그, 분석 결과, 분석 전 DB 덤프·파일 해시와 정상 종료 |
| `run-04/` | 분석을 재실행하지 않은 보존 비교의 준비 실패 기록 |
| `run-05/` | 최종 DB 덤프·파일·요약 비교와 정상 종료, `PASSED` |

`run-03/result.json`의 실패 판정은 후속 요약 검사 중단 기록으로 보존한다. 실제 분석 결과는 같은 디렉터리의 `analysis-verification.json`에 `VERIFIED`로 기록되어 있고, 최종 보존 판정은 `run-05/result.json`과 통합 요약으로 구분한다.

커밋 대상은 이 검증 문서와 수동 분석 실행 문서의 결과 링크다. 새 운영 패키지·클래스·테이블·의존성은 추가하지 않았다. 검증 보조 Java·PowerShell·Gradle init 파일은 `build/`에만 둔다. 보조 코드 컴파일과 실제 MySQL 분석·대조를 수행했으며 기존 JUnit이나 전체 테스트 모음은 재실행하지 않았다. 기존 증적을 지우는 `gradlew clean`도 실행하지 않았다.

`eligibilityOrHistoricalAvailabilityVerified=false`를 유지한다. 현재 종목 관측의 분석 재현은 종목 자격·신선도·과거 모집단·전략 순성과 검증을 대신하지 않는다. `AS_OF_VERIFIED`, `informationAvailableAt`, 후보 승인과 거래 허가를 새로 생성하지 않는다.
