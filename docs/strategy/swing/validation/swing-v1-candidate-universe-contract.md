# SWING_V1 백테스트 후보 Universe 선정·검증 계약

## 목적과 상태

이 문서는 백테스트 후보를 수익률이나 매매 신호를 보고 고르지 않고, 선정 당시 확인할 수 있었던 상장 정보와 유동성으로 재현 가능하게 구성하는 계약이다. 기존 `SWING_V1`의 진입·청산·수량·Risk 규칙은 변경하지 않는다.

```text
contractVersion: 1
contractStatus: DESIGN_ONLY
selectionMode: FIXED_INITIAL_COHORT
runtimeSelectionImplemented: false
```

**선정 계약을 정리한 상태이지 시장 전체 후보 선정이나 확장 표본 검증을 완료한 상태가 아니다.** 유동성 수치와 원천 데이터 출처는 별도 실험 계획에서 결과 확인 전에 확정해야 한다. 필수 조건이 비어 있거나 당시 정보를 검증할 수 없다면 검증용 Universe 실행을 허용하지 않는다.

[슬리피지 관측 07](swing-v1-slippage-observation-07.md)은 이미 본 네 종목의 계산과 비용 민감도를 확인했다. 작은 순이익이나 보유 비교 우위가 비용 증가로 사라졌으며, 시장 대표 표본·미사용 기간·양의 기대수익을 입증한 결과가 아니다. 다음 확장 실험에서도 손실과 무거래를 포함하고, 기존 관측을 이 계약으로 선정한 결과라고 재분류하지 않는다.

전체 Universe 선정 계약은 여전히 문서 설계 단계다. 일봉 거래대금 저장·보충과 독립적인 평균 계산·최소 기준 판정·동일 구간 정렬·유동성 조건의 선정 정책·누락 종목 보존 평가·저장 일봉의 평가 연결은 구현됐지만 종목 마스터·전체 자격 판정·선정 스냅샷 저장·운영 후보 자동 선정은 구현되지 않았다. 조회 진입점은 명시한 요청의 평가만 담당하며 계산기와 정책·평가 서비스를 운영 또는 백테스트 후보 선정에 연결하지 않았다. 운영 후보·주문·스케줄·Risk·AI Prompt는 바꾸지 않는다.

검증 표본을 선정하는 Universe와 거래마다 신호를 거르는 전략 Screener는 구분한다. 이 계약은 첫 평가 전 표본을 정하는 전자만 다룬다. 골든크로스·ATR·과거 전략 수익률로 후보를 선정하거나 운영 BUY 조건에 유동성 필터를 삽입하지 않는다.

### 일봉 거래대금 저장 경로

- `KisDailyPriceBarOutput.accumulatedTradingValue`는 기간별 시세 응답 `output2`의 `acml_tr_pbmn`을 읽는다. 기존 일봉 API 응답을 사용하며 거래대금 전용 호출을 추가하지 않는다.
- `DailyPriceBar.tradingValueKrw`와 DB `trading_value_krw`는 nullable `Long`/`BIGINT`다. 숫자 `0`은 확인된 0으로 보존하고, 필드 누락·`null`·공백은 미확인 `null`로 보존한다. 음수·숫자가 아닌 값·`Long` 범위 초과는 Provider의 영구 입력 실패로 처리한다. 종가 × 거래량으로 대체하지 않는다.
- 저장 계약은 응답 정수를 배율 적용 없이 `tradingValueKrw`에 보존한다. **공식 명세에서 누적 거래대금 필드·일봉 주기·시장 코드는 확인했지만 이 필드의 원 단위 배율과 시간외 포함 범위는 명시적으로 확인하지 못했다.** `Krw`라는 필드명이나 테스트 성공이 원천 단위 검증을 대신하지 않는다. 실제 유동성 계산에 사용하기 전에 동일 종목·일자·시장 범위의 공식 거래대금과 대조하고, 검증 결과·배율·세션 범위를 실험 원천 계약에 고정해야 한다.
- `TradingVenueScope`는 Broker에 의존하지 않는 `com.stock.market.price.history`의 enum이다. `KRX`, `NXT`, `INTEGRATED`를 사용한다. KIS Client가 실제 요청하는 `J`, `NX`, `UN`과 명시적으로 대응하며 DB에는 enum 이름을 문자열로 저장한다. 이 값은 **요청한 조회 범위**이며 KOSPI/KOSDAQ 소속, 과거 시장의 구성이나 세션 확정 여부를 증명하지 않는다.
- `DailyPriceBarEntity.toBar()`, 기존 DB 조회 서비스와 `HarnessDailyPriceBarSnapshot.from()`은 거래대금과 범위를 그대로 전달한다. 구 생성자와 구 JSON에서 새 필드가 없으면 두 값 모두 `null`이다. 새 스냅샷도 이 구분을 보존한다. 현재 설정을 과거 행에 대입하지 않는다.
- `V4__add_daily_price_trading_value.sql`은 두 nullable 컬럼만 추가한다. 기존 OHLCV·고유키는 유지한다. 저장 단위는 아직 `(symbol, trading_date)`이므로 같은 날짜의 여러 시장 범위를 동시에 저장하는 구조가 아니며 범위가 다른 기간을 검증 없이 합산하지 않는다.
- 증분 수집 서비스는 최신 저장일 이후만 조회한다. 이미 저장된 과거 거래대금이 `null`이어도 자동 재조회하지 않는다. 별도 보충 Runner도 기본 비활성화이며 수동 실행 인자로 명시적으로 켤 때만 호출한다. 저장·보충 구현은 실 DB 마이그레이션 적용이나 모의투자 서버 재시작을 포함하지 않는다.

원천 확인: [KIS 기간별 시세 공식 명세](https://apiportal.koreainvestment.com/apiservice-apiservice?/uapi/domestic-stock/v1/quotations/inquire-daily-itemchartprice), [KIS 공식 요청 예제](https://github.com/koreainvestment/open-trading-api/blob/main/examples_llm/domestic_stock/inquire_daily_itemchartprice/inquire_daily_itemchartprice.py), [KIS 공식 응답 필드 예제](https://github.com/koreainvestment/open-trading-api/blob/main/examples_llm/domestic_stock/inquire_daily_itemchartprice/chk_inquire_daily_itemchartprice.py). 확인일은 `2026-10-03`이며 실 Broker 호출 없이 공개 명세를 열람했다.

후속 [원천 의미 검증 결과 01](../../../market/price/history/validation/daily-price-trading-value-source-validation-01.md)에서 상세 명세와 보존 응답을 확인했다. 원 단위 가정은 세 날짜의 산술과 모순되지 않았지만 금액 배율·세션 범위의 공식 확인과 동일 범위 수치 대조는 완료되지 않았다. 이 조건을 추론으로 통과시키거나 `DESIGN_ONLY`를 해제하지 않는다. 부족한 증거와 후속 확인 범위는 해당 기록을 따른다.

### 기존 일봉 거래대금 보충 서비스

서비스는 `com.stock.market.price.history.collection.backfill`, 결과와 상태는 그 아래 `result` 패키지에 둔다. 호출 계약은 `backfill(DailyPriceHistoryRequest request, TradingVenueScope expectedVenueScope)`다. 기존 Provider와 KIS 설정의 페이지 상한·페이지 간 대기를 재사용한다. 새로운 Client·API·테이블·마이그레이션은 추가하지 않는다.

1. 종목 하나와 시작·종료 날짜, 기대 조회 범위를 명시한다. 요청 범위의 기존 행에서 거래대금 또는 범위가 `null`인 날짜를 찾는다. 알려진 저장 범위가 기대 범위와 다르면 호출 전에 실패한다. 기존 행이 없거나 모두 완전하면 `NO_TARGETS`이며 외부 조회·DB 변경을 하지 않는다.
2. 첫 누락 날짜부터 마지막 누락 날짜까지만 Provider에 요청한다. 중간에 완전한 날짜가 있어도 날짜별 호출로 쪼개지 않는다. KIS 페이지 상한을 넘으면 기존 Provider 오류를 그대로 전달하며 범위를 자동 확대하거나 무제한 재시도하지 않는다.
3. 응답 종목·날짜 범위·기대 시장 범위·알려진 거래대금과 기존 OHLCV를 검사한다. 조회 범위 안의 기존 저장 날짜가 응답에 없거나, 이미 알려진 값이 충돌하면 요청 전체를 실패시킨다. 중간의 완전한 기존 행도 검증하되 덮어쓰지 않는다. 응답에만 있는 날짜는 신규 일봉으로 삽입하지 않는다.
4. 외부 호출은 DB 트랜잭션과 행 잠금 밖에서 수행한다. 반영 직전에 별도 쓰기 트랜잭션에서 날짜순으로 행을 잠그고 `refresh`하여 현재 값을 재조회한다. 처음 읽은 행의 ID·OHLCV·알려진 값이 변했거나 다른 작업이 충돌 값을 채웠으면 중단한다. 같은 값으로 이미 채워진 필드는 보존한다.
5. 모든 행의 검증이 끝난 뒤 처음 누락 상태였던 행의 `null` 필드만 채우고 `flush`한다. 검증·DB 저장·커밋 실패 시 이번 요청의 변경은 전부 롤백한다. 다른 작업이 앞서 커밋한 값은 이 요청이 취소하거나 복구하지 않는다. 기존 행 수·ID·OHLCV는 바꾸지 않는다.

결과는 요청 범위, 실제 조회 범위, 기대 시장 범위와 `targetCount`·`fetchedCount`·`updatedCount`를 보존한다. 수량은 필드 개수가 아니라 일봉 행 수다. `BACKFILLED`는 한 행 이상 반영한 상태, `ALREADY_FILLED`는 조회 사이 다른 작업이 대상 모두를 같은 값으로 채워 이번 요청은 변경하지 않은 상태다. 성공 후 같은 요청을 반복하면 `NO_TARGETS`이며 외부 조회를 생략한다. 확인된 `0`도 알려진 값이며 다른 숫자로 덮어쓰지 않는다.

`TransactionTemplate`로 짧은 읽기·쓰기 구간을 나눈다. 이미 활성 트랜잭션 안에서 호출하면 외부 API 대기 중 트랜잭션을 유지하는 것을 막기 위해 즉시 거절한다. KIS 활성화 시 서비스 빈을 등록하고, 수동 Runner는 별도의 `market.price.history.collection.trading-value-backfill.enabled=true`일 때만 등록한다. Scheduler·Controller는 추가하지 않는다. 트랜잭션·잠금 방식은 [Spring 공식 트랜잭션 문서](https://docs.spring.io/spring-framework/reference/data-access/transaction/programmatic.html), [Spring Data JPA 잠금 문서](https://docs.spring.io/spring-data/jpa/reference/jpa/locking.html)를 따른다.

검증은 서비스 단위 테스트와 H2 통합 테스트로 한다. 누락 필드만 보충, 재실행 조회 생략, 실제 0 보존, 잘못된 응답·OHLCV 충돌·동시 갱신 거절, 두 요청의 동시 반영 및 DB 제약조건 오류 시 전체 롤백을 확인한다. H2 결과는 운영 MySQL의 잠금·타임아웃 검증을 대신하지 않는다.

이 변경에서는 실제 보충 호출·운영 DB 변경·Docker 조작을 하지 않는다. 실제 실행 전에 과거 확정 일봉 범위, 조회 시장 설정과 기대 범위 일치, 요청별 호출 예산·DB 잠금 대기 정책과 원본 보존 방법을 별도로 승인해야 한다. 서비스 자체는 일봉 확정 시각을 자동 판정하지 않으며 수동 Runner가 기존 날짜 정책의 최근 확정일을 검사한다. 이는 설정상 검사이지 원천 데이터 확정의 증명이 아니다. 실행 방법은 [일봉 거래대금 수동 보충](../../../market/price/history/daily-price-trading-value-backfill.md)을 따른다. **원천의 금액 단위·시간외 범위, 수정주가·기업행위와 과거 시점 정보 검증은 여전히 별도 과제다.** 기존 OHLCV 일치만으로 과거 원천이 완전히 검증됐다고 인정하거나 유동성 Universe를 실행하지 않는다.

## 선정 시점과 대상

### 기준 시점

- `T`: 첫 판단·체결 평가 거래일. 초기 일봉 근사에서는 첫 신호일의 다음 거래일이다.
- `S`: `T`의 직전 거래일이자 첫 신호 기준일이다. 일봉 입력은 `S`까지 확정된 값만 사용한다.
- `selectionCutoffAt`: 선정 정보가 알려져 있어야 하는 시각. `S` 일봉 확정 이후이고 첫 판단 시각보다 앞서거나 같아야 한다. 날짜만이 아니라 시간대가 있는 시각을 보존한다.
- `selectedAt`: 현재 시스템에서 선정을 계산한 시각. 과거 데이터의 의미상 기준 시각인 `selectionCutoffAt`와 구분한다.

휴장일을 고려한 직전·다음 거래일을 사용하며 단순히 날짜에서 하루를 빼거나 더하지 않는다. 일봉 날짜가 `S` 이전이어도 해당 값이나 상장 정보가 선정 기준 시각 이후에야 알려졌다면 과거 판단의 입력으로 자동 인정하지 않는다.

현재 수집 시각이 과거 기준 시각보다 늦다는 사실만으로 과거 자료를 모두 거절하지는 않는다. 당시 상장 구성과 당시 알려진 정보임을 입증하는 원천 자료·적용 시점·정정 이력을 별도로 확인해야 한다. 현재 종목 목록에 과거 날짜만 붙이거나 현재 수정된 일봉의 날짜만 확인한 것으로 이 검증을 대신하지 않는다. 원본 해시 고정은 재실행 증거이지 과거 정보 가용성의 증거가 아니다.

### 시장과 종목 유형

대상 시장은 KOSPI와 KOSDAQ의 개별주다. 보통주·우선주 등 세부 허용 유형은 `eligibleSecurityTypes`로 실행 전에 명시하며 암묵적으로 확대하지 않는다. ETF·ETN은 허용하지 않는다. 시장·유형·상장 상태를 확인할 수 없는 종목은 일반 주식으로 추정하지 않는다.

상장 구성은 `S` 당시의 자료를 사용한다. 그때 상장되어 있었지만 이후 상장폐지된 종목도 검토 모집단에 남겨야 한다. 나중에 상장된 종목은 초기 모집단에 넣지 않는다. 현재 생존 종목만 제공하는 원천 자료로는 과거 전체 시장을 재구성했다고 주장할 수 없다.

KOSPI 후보는 KOSPI 벤치마크, KOSDAQ 후보는 KOSDAQ 벤치마크의 별도 실험으로 평가한다. 현재 요청에는 벤치마크 하나만 있으므로 두 시장을 한 요청에 섞지 않는다. 시장 매핑은 향후 선정 자료에서 검증해 명시적으로 전달해야 하며 현재 자동 매핑 기능이 있다는 뜻은 아니다.

기준 시점의 거래정지 여부 등 추가 자격 제한을 적용한다면 원천 근거와 규칙을 사전에 고정한다. 이후 거래정지·상장폐지·시장 이전을 미리 알고 제외해서는 안 된다.

## 유동성 계산과 정렬

초기 기준은 **선정 기준일까지의 최근 N개 거래일 평균 거래대금**이다. N, 최소 평균 거래대금과 최대 후보 수는 이번 문서에서 임의의 기본 숫자로 정하지 않는다. 확장 실험의 입력 계약에서 빠짐없이 확정한다.

| 필수 항목 | 계약 |
| --- | --- |
| `lookbackTradingDays` | 양의 정수 N. 달력 일수가 아니라 거래일 수다. |
| `minimumAverageTradingValueKrw` | 양의 금액. 통화는 KRW이며 기준 충족은 `평균 >= 최소 금액`이다. |
| `maxCandidateCount` | 양의 정수. 기준을 충족한 후보 중 이 수까지 선택한다. |
| `liquidityMetric` | 초기 검증은 실제 일별 거래대금의 평균으로 고정한다. 근사 지표와 혼용하지 않는다. |
| `tradingVenueScope` | 거래대금의 시장 범위. 서로 다른 거래소·통합 범위 값을 혼합하지 않는다. |
| `eligibleSecurityTypes` | 명시한 개별주 유형만 허용하며 ETF·ETN이 포함되면 계획을 거절한다. |

입력은 `S`까지의 마지막 N개 거래일 목록에 대응해야 한다. 누락된 날을 제외해 N보다 작은 분모로 평균을 만들거나, N개를 채우려고 평가 기간의 거래일을 포함하지 않는다. 확인된 0원 거래대금은 0으로 포함하고 누락·알 수 없는 거래대금은 0으로 대체하지 않는다. 음수·중복 날짜·충돌한 원본은 입력 오류다.

```text
averageTradingValueKrw = sum(해당 N개 거래일의 실제 거래대금) / N

자격 조건과 유동성 최소 기준 통과
-> 평균 거래대금 내림차순
-> 동률이면 symbol 문자열 오름차순
-> 앞에서 maxCandidateCount개 선택
```

비교와 정렬에는 표시용 반올림 값을 사용하지 않는다. 금액 합산은 오버플로 없이 계산하고, 같은 N을 사용하는 후보의 평균 비교는 정확한 합계로도 가능하다. 종목 코드는 앞자리 0을 보존한 문자열로 취급한다. 중복 종목·빈 코드·시장이나 유형의 충돌은 중단 사유이며 DB 조회 순서에 따라 선택 결과가 바뀌면 안 된다.

현재 일봉의 `volume`은 주식 수량이며 거래대금이 아니다. `closePriceKrw * volume`도 실제 거래대금과 같다고 가정하지 않는다. 별도의 근사 지표를 연구하려면 계산 방식·가격과 거래량의 조정 기준·원천 범위를 고정한 새 선정 정책으로 기록한다. 실제 거래대금이 없다고 기존 기준에 이 값을 조용히 대입하지 않는다. 유동성 기준을 통과해도 실제 주문의 체결 품질을 보장하지 않는다.

### 독립적인 평균 계산기

`com.stock.strategy.universe.liquidity`의 `DailyTradingValueAverageCalculator`는 기존 `DailyPriceHistory`, 선정 기준 거래일 `selectionAsOfDate`, 필요한 N개 날짜 목록과 기대 `TradingVenueScope`를 받는다. 날짜 목록은 비어 있지 않은 엄격한 오름차순이며 중복·null·기준일 이후 날짜를 허용하지 않는다. 마지막 날짜는 기준일과 같아야 한다. `selectionAsOfDate`는 이 문서의 `S` 날짜이며 실제 정보 제공 시각인 `selectionCutoffAt`를 대체하지 않는다.

호출부가 검증한 정확한 최근 N개 거래일 목록을 전달해야 한다. 계산기는 휴장일 달력이나 DB로 날짜를 생성하지 않고 목록이 실제 거래일 또는 연속된 최근 거래일인지 증명하지 않는다. `getLatestDailyPriceHistoryAtOrBefore()`의 최근 N개 저장 행만으로 이 목록을 대체하면 중간의 누락 거래일을 건너뛸 수 있다.

계산은 지정 날짜의 일봉만 사용한다. 누락 일봉·null 거래대금·미확인 시장 범위는 `Optional.empty()`다. 알려진 시장 범위가 기대 범위와 다르면 `IllegalArgumentException`이며 다른 날짜의 누락이 있어도 충돌 검사를 생략하지 않는다. 목록 밖의 과거·미래 일봉은 합산이나 메타데이터 검증에 사용하지 않는다. 알려진 0은 분모에 포함하고 전부 0인 입력도 유효한 계산 결과다. 잘못된 날짜 구조는 예외이며 누락 데이터를 더 오래된 일봉이나 미래 일봉으로 보충하지 않는다.

결과 `DailyTradingValueAverage`는 종목·기준일·불변 날짜 목록·시장 범위·`BigInteger` 합계를 보존하고 `tradingDayCount()`로 목록 크기인 N을 반환한다. 별도의 반올림 평균은 저장하지 않는다. 평균의 정확한 표현은 합계/N이다. `meetsMinimumAverageTradingValueKrw(long minimumAverageTradingValueKrw)`는 명시한 양의 정수 기준 M에 대해 `합계 >= M × N`을 `BigInteger` 곱셈·비교로 판정한다. 기준과 같으면 `true`, 미달이면 `false`이며 0·음수 기준은 `IllegalArgumentException`이다. 곱셈 결과가 `long` 범위를 넘어도 정확성을 유지한다.

이 메서드는 완전한 계산 결과의 수학적 기준 판정일 뿐 종목 자격이나 원천 검증 결과가 아니다. 계산기의 `Optional.empty()`를 미달인 `false`로 대체하지 않는다. 운영 최소 금액·기본값·설정 항목은 추가하지 않았으며 전체 Universe 선정은 구현하지 않았다. 테스트는 기준 일치·합계가 경계보다 1원 작거나 큼·0 합계·서로 다른 분모·큰 금액·잘못된 기준을 합성 데이터로 확인한다.

계산기 성공은 원천 통화·배율·세션·기업행위·과거 정보 가용성의 확인을 뜻하지 않는다. 현재 KIS 원천의 미검증 조건을 그대로 유지하며 실제 유동성 선정에는 연결하지 않는다. 단위 테스트는 합성 자료의 정확한 합계·0·누락·시장 충돌·잘못된 날짜·미래 자료 무시·큰 합계·입력 순서와 결과 불변성을 검증한다. DB·외부 API·모의투자 수익성의 검증은 아니다.

### 동일 거래일 구간의 순위 계산

`com.stock.strategy.universe.liquidity.ranking`의 `DailyTradingValueRankingPolicy.rank(List<DailyTradingValueAverage> averages)`는 완전한 계산 결과만 받아 불변 정렬 목록을 반환한다. 모든 결과의 `selectionAsOfDate`, 전체 `tradingDates`와 `tradingVenueScope`가 일치해야 한다. 날짜 수나 마지막 날짜만 같아도 중간 날짜가 다르면 `IllegalArgumentException`으로 거절한다. 중복 종목도 거절하며 합계가 같은 중복 입력을 자동으로 합치지 않는다. `null` 목록·항목은 `NullPointerException`, 빈 목록은 불변 빈 목록이다.

전체 날짜 목록이 같으므로 분모가 같다는 것을 검증한 뒤 `BigInteger` 합계 내림차순으로 비교한다. 동률이면 앞자리 0을 보존한 `symbol` 문자열 오름차순이다. 평균을 정수로 나누거나 부동소수점·표시용 반올림으로 변환하지 않아 큰 합계와 1원 차이를 보존한다. 입력 목록의 순서를 바꾸지 않고 새 목록을 반환하며, 확인된 0을 포함한 입력 결과 모두를 남긴다. 최소 거래대금 판정·상위 개수 제한·선정 상태·탈락 사유는 이 정책의 책임이 아니다.

이 정렬은 전달된 결과 사이의 순서일 뿐 전체 시장 모집단의 검증이나 후보 선정 완료가 아니다. 호출부가 누락·미확인 종목을 보존하고 실제 거래일·원천 단위·시장 및 종목 자격·과거 정보 가용성을 별도로 검증해야 한다. 거래정지와 기업행위 처리도 추가하지 않았다. 합성 테스트는 정확한 정렬·동률의 입력 순서 독립성·0 유지·큰 금액·비교 조건 충돌·중복·불변성을 확인하며 외부 API·DB·Docker를 사용하지 않는다.

### 거래대금 기준 후보 선정 정책

`com.stock.strategy.universe.liquidity.selection`의 `DailyTradingValueSelectionPolicy`는 `select(List<DailyTradingValueAverage> averages, long minimumAverageTradingValueKrw, int maxCandidateCount)`로 호출한다. 최소 거래대금과 최대 개수는 호출자가 명시한 양수여야 하며 빈 목록이어도 0·음수 기준은 `IllegalArgumentException`으로 거절한다. 기본값이나 운영 설정은 추가하지 않았다.

기존 `DailyTradingValueRankingPolicy.rank()`로 전체 입력을 먼저 검증·정렬한다. 기준 미달 또는 개수 제한으로 제외될 항목도 중복 종목·기준일·전체 날짜 목록·시장 범위 검사를 통과해야 한다. 잘못된 항목을 미리 필터링해 입력 충돌을 숨기지 않는다. `null` 목록·항목은 순위 정책의 예외를 그대로 전달한다.

정렬된 결과마다 기존 `meetsMinimumAverageTradingValueKrw()`로 정확한 최소 기준을 판정한다. 미달이면 `LIQUIDITY_BELOW_MINIMUM`, 통과하면 최대 개수까지 `SELECTED`, 이후는 `CANDIDATE_LIMIT`이다. 미달 항목은 선정 개수를 채우지 않으며 개수 제한에 도달한 뒤에도 미달 사유를 우선한다. 기준을 통과한 종목이 적으면 후보 수를 억지로 채우지 않는다.

`selection.result`의 `DailyTradingValueSelectionResult`는 원래 `DailyTradingValueAverage`, `rank`, `DailyTradingValueSelectionStatus`를 보존한다. `rank`는 전달된 모든 완전한 계산 결과 안에서 정렬한 1부터 시작하는 순번이며, 동률도 종목 코드 순서에 따라 서로 다른 순번이다. 전체 시장 순위나 선정된 종목만의 순위가 아니다. 미달·개수 제한을 포함해 입력마다 결과 한 개를 반환하며 원본 목록을 바꾸지 않는 불변 목록이다. 빈 입력과 유효한 기준이면 불변 빈 목록이다. 선정 개수는 호출별 지역 변수이며 이전 호출 상태를 유지하지 않는다.

이 enum의 `SELECTED`는 **유동성 조건상 선정**만 뜻한다. 종목 유형·상장 상태·거래정지·기업행위·원천 단위·과거 정보 가용성의 확인이나 주문 허가를 뜻하지 않는다. 미확인 종목은 입력 결과가 없다고 미달로 바꾸거나 누락해서는 안 된다. 아래 평가 서비스가 전달된 대상의 계산 불가 종목을 별도 목록으로 보존하지만, 전체 Universe의 `DATA_UNVERIFIED` 근거와 원천 검증은 여전히 호출부의 책임이다. 선정 정책 자체는 `Optional.empty()`를 받거나 확인 불가 종목을 분류하지 않는다. 결과 목록은 영속화된 선정 스냅샷이 아니며 사용한 기준과 전체 모집단의 근거 저장도 후속 과제다.

테스트는 정확한 최소 경계·최대 개수·미달 사유 우선·0과 무선정·동률의 입력 순서 독립성·큰 합계·잘못된 기준·제외될 입력의 충돌·결과 값과 불변성·정책 재사용을 합성 데이터로 확인한다. 운영 후보·DB·외부 API·Docker에는 연결하지 않으며 `DESIGN_ONLY`와 `runtimeSelectionImplemented=false`를 유지한다.

### 대상 전체 평가와 누락 종목 보존

`com.stock.strategy.universe.liquidity.evaluation`의 `DailyTradingValueSelectionEvaluationService.evaluate(request, histories)`는 평가 요청과 종목별 시세 목록을 따로 받는다. `evaluation.request`의 `DailyTradingValueSelectionEvaluationRequest`는 `targetSymbols`, `selectionAsOfDate`, `requiredTradingDates`, `expectedVenueScope`, `minimumAverageTradingValueKrw`, `maxCandidateCount`를 명시적으로 보존하는 record다. 시세 객체 자체가 없는 종목도 대상 목록을 기준으로 누락을 발견한다. 전달된 대상이 실제 시장 전체 또는 과거 시점의 적격 모집단이라는 것을 증명하는 서비스는 아니다.

요청 생성 시 대상 목록은 비어 있지 않아야 하며 null·빈 코드·중복 코드를 거절한다. 대상은 코드 오름차순으로 정렬한 불변 복사본으로, 거래일 목록은 기존 `DailyTradingValueAverage.copyValidatedTradingDates()`의 구조 검증을 재사용한 불변 복사본으로 보존한다. 원본 목록을 바꾸지 않으며 이후 원본 변경도 요청에 반영되지 않는다. 시세를 받기 전에 잘못된 날짜 구조·미확인 기대 시장 범위·0 또는 음수 최소 금액·최대 개수를 거절하므로 모두 누락된 경우도 잘못된 기준으로 평가하지 않는다. 이 날짜 검증은 실제 거래일 달력이나 원천의 확정 시각을 확인하지 않는다.

서비스의 null 요청·시세 목록·시세 항목, 중복 시세 종목과 대상 밖 시세는 입력 오류다. 빈 시세 목록은 입력 오류가 아니라 대상 모두의 데이터 누락이다. 시세는 요청 record에 포함하지 않으며 이번 변경은 일봉 원본·해시·출처 증거를 추가로 보존하지 않는다.

대상 코드를 문자열 오름차순으로 순회하며 기존 계산기를 호출한다. 시세가 없거나 계산기가 `Optional.empty()`를 반환하면 `unverifiedSymbols`에 남긴다. 성공한 계산은 `calculatedAverages`에 보존하고 확인된 0도 성공한 계산이다. 누락을 찾았다고 나머지 계산을 중단하지 않으며, 다른 종목의 알려진 시장 범위 충돌은 예외로 그대로 전달한다. 예상하지 못한 계산 실패도 확인 불가로 바꾸지 않는다. 필요한 날짜 밖의 과거·미래 일봉은 기존 계산기의 제외 규칙을 그대로 따른다.

`evaluation.result`의 `DailyTradingValueSelectionEvaluationResult`는 `request`, `status`, `calculatedAverages`, `unverifiedSymbols`, `selectionResults`를 보존한다. 서비스는 받은 불변 요청을 그대로 결과에 전달하므로 전부 미확인인 경우도 대상 전체·기준일·거래일 목록·시장 범위·최소 금액·최대 후보 수가 남는다. 누락이 하나라도 있으면 `INCOMPLETE`와 빈 선정 결과를 반환하고 선정 정책은 호출하지 않는다. 모두 계산되었을 때만 `COMPLETE`로 기존 선정 정책에 전체 계산 결과와 요청의 최소 금액·최대 개수를 전달한다. 따라서 성공한 종목만으로 부분 후보를 확정하거나 누락을 거래대금 미달로 처리하지 않는다.

서비스가 반환하는 계산 목록과 확인 불가 목록은 코드 오름차순, 선정 결과는 기존 거래대금 내림차순·동률 코드 오름차순이다. 입력 종목·시세 순서가 달라도 요청을 포함한 같은 결과를 내고 원본 목록을 변경하지 않는다. 결과 record는 요청 null과 상태·목록의 모순, 중복·겹치는 종목을 거절하고 세 목록을 방어적으로 복사한다. 계산 성공과 미확인 종목의 합집합은 요청 대상과 정확히 같아야 한다. 분류 건수만 같은 다른 종목 집합이나 빠진 대상·대상 밖 종목도 거절한다. 계산값마다 기준일·전체 거래일 목록·시장 범위가 요청과 일치해야 하며, 계산값끼리만 같은 잘못된 구간도 통과시키지 않는다. 완전한 결과에서 빠지거나 변경된 계산 값·중복 선정 항목·연속되지 않은 순위도 기존처럼 거절한다. 거래대금 계산·정렬·선정 상태 판정은 기존 정책을 재사용하고 결과 record에서 별도 알고리즘으로 재구현하지 않는다.

`COMPLETE`는 **전달된 대상의 수학적 계산·분류 완료**일 뿐 모집단·원천·과거 정보 가용성 검증이나 주문 권한을 의미하지 않는다. 알려진 0 때문에 전부 미달인 경우도 계산은 완료될 수 있으므로 `COMPLETE`만으로 후보 존재나 검증용 실행 허가를 판정하지 않는다. 계산 불가 원인이 거래정지·수집 실패·실제 이력 부족 중 무엇인지는 이 서비스가 추정하지 않는다. 요청 조건은 인메모리 결과에 남지만 원본·정책 버전·기준 시각의 정보 가용성·전체 모집단의 근거와 DB 저장은 후속 과제다. 현재 결과는 영속화된 선정 스냅샷이 아니며 요청만으로 정정 전 원본을 재현할 수 있다고 주장하지 않는다.

합성 테스트는 요청의 입력 검증·정렬·방어적 복사, 완전·불완전 결과의 기준 보존, 요청 대상과 분류 집합의 정확한 일치, 요청과 다른 날짜·시장 범위 거절을 확인한다. 전체 계산과 기존 정책 호출, 명시한 최소 금액·최대 개수 반영, 시세 객체·필수 날짜·메타데이터 누락 보존과 선정 미호출, 0과 누락 구분, 미래 데이터 무시, 큰 금액, 누락 이후 충돌·예외 전파, 입력 순서 독립성·정책 재사용·불변성도 확인한다. DB 조회·외부 API·수집·운영 후보 연결·Docker 조작을 추가하지 않으며 `DESIGN_ONLY`와 `runtimeSelectionImplemented=false`를 유지한다.

### 저장된 일봉 조회와 평가 연결

`com.stock.strategy.universe.liquidity.evaluation.query`의 `DailyTradingValueSelectionQueryService.evaluate(request)`는 기존 평가 요청을 받는 저장 데이터 진입점이다. `DailyPriceHistoryQueryService`와 `DailyTradingValueSelectionEvaluationService`만 의존한다. 기존 평가 서비스는 DB를 의존하지 않아 별도 파일·합성 이력으로 계산하는 경로도 그대로 유지한다.

요청 대상 전체를 코드 순서대로 순회하며 각 종목의 `DailyPriceHistoryRequest`를 만들어 조회한다. 시작일은 `requiredTradingDates`의 첫 날짜, 종료일은 `selectionAsOfDate`다. 기존 기간 조회는 저장 일봉의 해당 범위를 읽고, 실제 합산은 계산기가 명시된 거래일 목록에만 적용한다. 범위 안에 있어도 필수 목록에 없는 날짜는 합산하지 않는다. `최근 N개`나 다음 시가 조회로 이력이 부족한 날짜를 대체하지 않으며, 기준일 이후 자료를 선정에 사용하지 않는다.

저장 행이 없는 종목도 종목 코드와 빈 목록이 있는 `DailyPriceHistory`로 보존한다. 전체 대상의 조회가 끝난 뒤 불변 이력 목록과 원래 요청을 평가 서비스에 한 번 전달하고 그 결과를 그대로 반환한다. 대상 목록을 DB에 존재하는 종목 목록으로 축소하지 않는다. 하나라도 누락·미확인 데이터이면 기존 평가의 `INCOMPLETE`와 선정 차단이 유지되고 확인된 0은 알려진 계산값으로 남는다.

null 요청은 조회 전에 거절한다. 조회가 예기치 않게 null 이력을 반환하거나 요청한 종목과 다른 종목을 반환하면 오류로 거절하며, 다른 요청 대상 종목의 응답이어도 대체하지 않는다. DB 조회·이력 변환 실패는 빈 이력으로 바꾸지 않고 그대로 전달한다. 일부 종목을 읽은 뒤 실패하면 나머지 조회와 전체 평가를 진행하지 않는다. 평가 단계의 알려진 시장 범위 충돌이나 예상하지 못한 실패도 그대로 전달하며 부분 성공으로 바꾸지 않는다.

새 서비스는 저장·보충 기능을 호출하지 않고 외부 Provider도 의존하지 않는다. 종목별 기존 기간 조회를 재사용하는 제한된 명시 대상의 경로이며, 전 시장 일괄 조회·성능 최적화·Controller·Runner·Scheduler는 추가하지 않는다. 운영 DB·Docker·기존 수집 설정·운영 후보·백테스트 후보 연결을 변경하지 않는다.

단위 테스트는 정확한 기간·전체 대상 조회와 평가 순서, 빈 이력·미확인 메타데이터·0의 구분, 기준 전달, 잘못된 조회 응답과 조회 실패 시 평가 미호출, 평가 예외·정책 재사용을 확인한다. H2 통합 테스트는 저장·복원된 같은 원본의 직접 평가와 결과 일치, 없는 대상 보존, 오래된·미래·대상 밖 일봉 제외, 필수 날짜와 조회 범위의 구분, 알려진 시장 충돌, 단일 날짜와 재실행, 기존 행의 ID·종목·값 보존을 확인한다. 테스트 데이터는 합성이며 운영 MySQL 성능·동시 갱신·격리 검증이나 실제 원천 의미 확인을 대신하지 않는다.

이 연결은 현재 DB에서 읽은 값의 계산 경로일 뿐 과거 정보 가용성을 증명하지 않는다. 여러 종목의 조회가 하나의 고정 DB 시점 스냅샷임을 보장하는 새 격리 계약도 추가하지 않았으며, 원본 정정·동시 보충 이후까지 같은 결과를 재현할 근거는 별도 보존해야 한다. 거래대금 단위·세션 범위·실제 거래일·과거 모집단과 종목 자격의 미검증 상태를 유지한다. `COMPLETE`를 검증용 Universe 실행 승인으로 사용하지 않으며 `DESIGN_ONLY`와 `runtimeSelectionImplemented=false`를 유지한다.

## 고정 후보와 데이터 부족

최초 구현은 기간 시작에 한 번 선정하고 끝까지 유지하는 `FIXED_INITIAL_COHORT`다. 기간 중 신규 상장, 유동성 순위 변화나 성과를 보고 후보를 보충하지 않는다. A·B·C처럼 시작일이 다른 실험은 각 시작 시점의 자료로 따로 선정할 수 있지만, 결과를 확인한 뒤 이전 기간의 후보를 수정하지 않는다.

이 방식은 **시작 시점의 선정 종목 집단**을 검증한다. 평가 기간 동안의 전체 시장을 매일 재구성하는 동적 Universe가 아니다. 정기 재선정이나 보유 종목 퇴출·교체는 현재 백테스트의 범위 밖이며 별도 운용 계약이 필요하다.

### 선정 당시 이력 부족

선정 계획에는 `requiredPreselectionBarCount`를 고정한다. 현재 관측과 같은 최근 120개 이력을 사용할 실험이면 120으로 명시한다. 통합 기술 분석의 최소 61개와 실행에 사용할 조회 수량은 같은 개념이 아니므로 암묵적으로 대체하지 않는다.

첫 신호일까지 이미 확인 가능한 선행 이력이 정해진 수량보다 적으면 `INSUFFICIENT_PRESELECTION_HISTORY`로 기록한다. 이는 선정 당시 알 수 있는 자격 부족이다. 상장 이력이 충분한데 저장 데이터만 부족하거나 출처가 불명확한 경우는 자격 부족으로 확정하지 않고 `DATA_UNVERIFIED`로 구분한다. 과거 자료 보충 여부를 확인하기 전에 성공한 조회 종목만 골라서는 안 된다.

### 선정 후 평가 데이터 누락

후보가 고정된 뒤에는 종료일까지의 일봉 존재 여부, 다음 평가 시가 존재 여부나 관측 수익률로 후보를 삭제·대체하지 않는다. 다음 거래일 시가와 평가 기간 데이터는 실행에 필요한 미래 결과 자료이지 초기 선정 조건이 아니다.

향후 수집은 고정된 후보를 대상으로 할 수 있지만 수집 실패·누락·기간 중 거래정지·상장폐지 때문에 평가를 완료하지 못하면 그 후보와 실패를 보존한다. 검증된 자료를 보충한 뒤 같은 선정 스냅샷으로 재실행하거나, 현재 평가기가 해당 사건을 처리하지 못한다면 실험을 불완전 상태로 남긴다. 마지막 가격을 복사해 임의로 성공한 평가곡선을 만들지 않는다.

현재 실험 서비스는 종목 평가일과 벤치마크 날짜 일치를 요구하며 일부 실패를 제외한 성공 반환을 허용하지 않는다. 이 제한 때문에 전체 실험이 실패해도 선정 후보를 줄여 통과시키지 않는다. 실제 기업행위·상장폐지 정산·정지 기간 처리가 구현되어 있다는 뜻도 아니다.

## 선정 상태와 보존할 증거

선정 대상 전체를 포함·제외·확인 불가로 분류하고, 모집단 수가 분류 건수 합계와 일치해야 한다. 유동성 기준을 통과했지만 최대 후보 수에 걸린 종목도 순위와 사유를 남긴다. 다음 표는 전체 Universe에서 향후 저장할 의미다. 현재 Java 선정 enum에는 유동성 조건만 판단하는 `SELECTED`·`LIQUIDITY_BELOW_MINIMUM`·`CANDIDATE_LIMIT`만 있다. 평가 서비스의 `INCOMPLETE`와 `unverifiedSymbols`는 전달된 대상의 계산 불가를 보존하는 수단이며, 나머지 자격·원천 검증 사유와 전체 모집단 처리는 구현하지 않았다.

| 분류 / 사유 | 의미 |
| --- | --- |
| 포함 / `SELECTED` | 자격·유동성 기준을 통과하고 최대 후보 수 안에 든 종목 |
| 제외 / `UNSUPPORTED_SECURITY_TYPE` | 기준 시점에 확인된 ETF·ETN 또는 허용하지 않은 개별주 유형 |
| 제외 / `NOT_ELIGIBLE_AS_OF` | 기준 시점의 시장·상장·사전 확정 자격 조건을 충족하지 않은 종목 |
| 제외 / `INSUFFICIENT_PRESELECTION_HISTORY` | 기준 시점에 확인된 실제 선행 이력의 부족 |
| 제외 / `LIQUIDITY_BELOW_MINIMUM` | 완전한 입력으로 계산한 평균 거래대금이 최소 기준보다 작음 |
| 제외 / `CANDIDATE_LIMIT` | 자격·유동성은 통과했지만 고정 최대 후보 수를 넘은 종목 |
| 확인 불가 / `DATA_UNVERIFIED` | 모집단·유형·상장 상태·시점·이력·거래대금 등의 근거 부족 |

확인 불가 종목을 제외 처리해 과거 시장 전체 Universe가 완성됐다고 주장하지 않는다. 모집단 출처의 완전성 또는 자격 판정에 필요한 자료를 확인할 수 없으면 검증용 선정은 준비되지 않은 상태다. 원천 범위가 좁은 표본을 연구한다면 그 범위와 미확인 건수를 따로 기록하고 시장 전체 검증과 구분한다.

보존할 스냅샷은 다음을 포함한다. 아래 이름은 설계상 의미이며 이번에 저장 기능을 구현하지 않는다.

| 구분 | 내용 |
| --- | --- |
| 계획 | 실험 ID, 선정 정책 ID·버전, 코드 revision, 전략 ID·버전, 시장과 벤치마크 |
| 시점 | `S`, `T`, `selectionCutoffAt`, `selectedAt`, 신호 및 실제 평가 기간 |
| 기준 | 유형, N, 최소 거래대금, 최대 후보 수, 선행 이력 수량, 시장 범위와 추가 자격 제한 |
| 모집단 | 원천 종목 목록, 기준일의 상장·시장·유형, 적용 시점·당시 정보 가용성의 근거 |
| 시세 | 선정용 일봉·거래대금의 날짜·값·단위·조정 여부·출처·자료 버전·수집 시각 |
| 결정 | 포함·제외·확인 불가 전체 목록, 종목별 계산 값·순위·사유, 최종 후보와 순서 |
| 재현성 | 원본 파일과 해시, 선정 입력·결과의 해시, 비교 방식과 검산 결과 |
| 평가 연결 | 초기 자금·비용·Risk·전략 설정, 실행 ID, 성공·실패·무거래 결과 및 입력 스냅샷 참조 |

설정과 원본은 결과 확인 전에 고정하고 이후 수정본은 새 실험 ID로 보존한다. 정정된 데이터나 새 자료를 원본에 덮어써 과거 선정 결과를 바꾸지 않는다. API Key·Secret·토큰과 계좌 접속 정보는 증거에 넣지 않는다. 해시만 남기지 않고 재실행에 필요한 원본도 보존한다.

현재 요청에는 선정 정책·원천 스냅샷 필드가 없다. 초기 연결은 외부 실험 계획과 후보 스냅샷을 보존한 뒤 최종 목록을 `candidateSymbols`에 명시하는 방식으로 가능하다. 현재 서비스가 스냅샷을 자동 저장·검증한다거나 자동 선정 기능이 있다는 뜻은 아니다.

백테스트 표본 변경은 선정 정책과 실험 ID로 구분하고 이전 결과와 섞지 않는다. 기존 `SWING_V1` 정책을 호출하는 표본 선정 때문에 진입·청산 코드를 수정하지 않는다. 향후 운영 Universe 자동 갱신이나 Screener 변경을 실제 주문 흐름에 적용할 때는 기존 전략 실험 문서의 `strategyVersion` 증가 규칙을 따른다.

## 실행 준비 및 검증 기준

확장 평가 전에는 다음 조건을 모두 확인해야 한다.

1. 대상 시장·유형·선정 기준 시점·기간·유동성 수치·선행 이력·비용·Risk와 비교 기준을 확정한다. 필수 값에 숨은 기본값을 사용하지 않는다.
2. 기준 시점 모집단과 필요한 데이터 출처를 확인하고, 생존 편향·시점 정보·수정주가·기업행위의 미검증 범위를 명시한다.
3. 과거 시점 자료를 사용할 수 있는지 확인한다. 자료가 없다면 현재 상장 종목으로 대체하지 않고 검증용 과거 Universe 준비를 중단한다.
4. 고정한 선정 입력으로 후보와 전체 사유 목록을 만들고 독립 검산·재실행을 확인한다. 후보가 비거나 확인 불가 문제가 남으면 검증 완료로 취급하지 않는다.
5. 선정 스냅샷을 고정한 뒤 평가 자료를 준비한다. 이 단계의 데이터 부족이 초기 선정 목록을 바꾸지 않도록 한다.
6. 같은 전략·비용 경로로 전체 후보를 평가한다. 모든 후보를 요청 순서대로 확인하고 실패·무거래도 기록한다.

향후 선정 구현을 검증할 최소 사례는 다음과 같다. 이번 변경에서 테스트 클래스나 실행 결과를 만든 것은 아니다.

| 사례 | 기대 결과 |
| --- | --- |
| 같은 원본·기준, 입력 종목 순서만 변경 | 같은 후보와 최종 순서, 종목별 동일 사유 |
| 평균이 최소 금액과 같음 / 작음 | 각각 유동성 통과 / 제외 |
| 거래대금 동률, 앞자리 0이 있는 코드 | 코드 문자열 순서로 안정적인 후보 선정 |
| 최대 후보 수 초과 | 정해진 순위까지만 포함, 나머지는 `CANDIDATE_LIMIT` |
| 선정 기준일 다음 날짜의 데이터가 입력에 추가됨 | 선정 계산에 사용하지 않으며 후보·사유가 유지됨 |
| 선정 이후에 발표된 정보만 존재함 | 과거 선정 근거로 인정하지 않으며 확인 불가 처리 |
| 기준일에 상장, 이후 상장폐지 | 초기 모집단에서 사후 삭제하지 않음 |
| 현재 목록만 있고 기준일 구성 증거가 없음 | 과거 전체 시장 재구성으로 검증 완료 처리하지 않음 |
| ETF·ETN / 종목 유형 불명 | 각각 확인된 제외 / 확인 불가, 일반 주식으로 추정하지 않음 |
| 확인된 0 거래대금 / 거래대금 누락 | 각각 N개 평균에 0 포함 / 확인 불가, 같은 값으로 대체하지 않음 |
| 실제 거래대금 없이 OHLCV만 존재 | 종가 × 거래량을 실제 거래대금으로 대입하지 않음 |
| 기준일까지 필요한 실제 이력이 부족함 | 선행 이력 부족 사유 보존 |
| 저장 이력만 부족하여 실제 자격을 모름 | 자격 미달과 구분하고 보충 가능성·출처 확인 |
| 선정 후 평가 일봉이나 다음 시가가 없음 | 후보 유지, 실험 실패·불완전 보존, 조용한 삭제·대체 금지 |
| 결과가 손실 또는 무거래임 | 후보와 결과를 그대로 보존 |
| 원본 중복·시장 충돌·잘못된 기준·해시 변화 | 입력 검증 실패, 기존 증거 덮어쓰기 금지 |

확장 평가에서는 청산비용 반영 수익률, MDD, 완료 거래 수, 이익 집중도, 무거래 비율과 자금 노출을 시장·기간별로 함께 비교한다. 동일 종목 보유 비교도 같은 비용을 사용한다. 서로 독립적인 종목 결과를 공유 현금 계좌 수익률로 합치거나 수익률 하나로 전략을 승격하지 않는다.

이미 확인한 기간과 종목은 미사용 구간으로 재지정하지 않는다. 실제 미사용 기간·Walk-Forward·모의투자 실행의 통과 기준은 별도 계획에서 결과 확인 전에 정해야 하며 이번 문서가 이를 대신하지 않는다.

## 완료 범위와 남은 준비

이번 문서의 완료 기준은 선정 입력·시점·정렬·실패·증거 계약과 현재 구현의 차이가 명확하고, 같은 기준일·원본·설정으로 같은 후보를 재현할 방법을 설명할 수 있는 것이다. 후보 수를 늘리거나 수익성 검증을 완료한 것으로 계산하지 않는다.

현재 남은 준비는 기준 시점의 종목 구성·유형·상장 상태 원천 확인, 실제 거래대금과 시점 정보의 확보, 실험별 숫자 기준 확정, 원본 보존 및 선정 계산·검증 구현이다. 전체 시장을 무제한 조회하는 Broker 호출, Redis 등 인프라 추가나 운영 후보 확대는 이 계약만으로 허용하지 않는다. 수집 범위·예산과 실패 정책은 별도 구현 전에 확정한다.

과거 모집단과 기업행위 자료를 확보할 수 없다면 그 한계를 공개한 고정 표본 연구와 향후 시점부터 수집하는 모의투자 검증을 구분한다. 이 계약 자체는 수익을 보장하거나 실제 주문 권한·자금 한도를 확대하지 않는다.
